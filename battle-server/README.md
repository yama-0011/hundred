# ホーム → バトル：カードマスタ・保存デッキ・ドロー検証

実装を追加しました。依頼どおり、依存関係のインストール、DB初期化、ビルド、サーバー起動、ブラウザ確認、テスト実行は行っていません。

## 今回の経路

```text
ホーム用のマスタJSON（編集元は1か所）
    ↓ setup / seed による登録・公開
WorkersのローカルD1（変更不可の公開マスタ＋保存デッキ）
    ↓ 認証付き内部HTTP API
ASP.NET Coreバトル（マスタ・デッキ検証）
    ↓ 対戦用の個体40枚を生成・シャッフル
初期手札4枚＋以降のドロー → Unityに同期
```

既存の `workers/apps-api` は変更していません。検証用の `workers/card-home-poc` を追加しています。AWS・Cloudflareへのデプロイは行いません。

## 1. ホームの初期化（初回のみ）

Hundredのターミナルで実行します。npmと、採用したWranglerが動作するNode.js環境が必要です。

```bash
bash scripts/card-home-poc.sh init
```

このコマンドは依存関係をインストールし、内部API用のランダムキーを生成し、ローカルD1へテーブル・公開マスタ・初期デッキを登録します。マイグレーションの確認が表示されたら適用してください。

- 公開マスタ：`poc-001`、スキーマ：`1`、ルール：`core-1`
- マスタは16種類、すべて効果なしスピリット
- 最初の14種類は従来の赤の仮カードと同じ性能
- 追加2種類は紫（コスト0）と緑（コスト1）。データから属性・コストが反映される検証用
- 初期デッキID：`deck-poc`、40枚

内部APIキーは `workers/card-home-poc/.dev.vars` に保存し、Git対象外です。バトルは起動時に同じファイルからキーを読みます。キーをUnityへ送信しません。

## 2. ホームを起動

```bash
bash scripts/card-home-poc.sh start
```

`http://127.0.0.1:8788` を開きます。カードの採用枚数を選び、40枚で保存します。

- 保存ごとに新しいデッキIDを発行します。
- 保存済みのデッキを読み込み、編集後に別IDで保存できます。
- 保存後の内容は変更しません。進行中の試合へ編集が混入しないようにするためです。
- コピーするIDは最後に保存・読込したデッキのIDです。未保存の変更を使う場合は先に保存してください。

## 3. バトルをビルド・起動

旧バトルサーバーをCtrl+Cで停止し、別のターミナルで実行します。

```bash
bash scripts/card-battle-poc.sh build
bash scripts/card-battle-poc.sh start
```

ホームの初期化後にバトルを起動してください。

`http://127.0.0.1:5080` を2画面で開きます。Unityロビーに追加した「保存デッキID」へホームでコピーしたIDを入力します。双方で違うデッキを選べますが、公開マスタのバージョンは同じ必要があります。

最初の画面でルーム作成 → もう片方でルームIDを入力して参加します。

## 4. 画面での確認

1. ホームの初期デッキを読み込み、赤カード1種類の3枚を0枚にし、紫カードを3枚追加して40枚で保存します。
2. Player 1にそのID、Player 2に `deck-poc` を指定して参加します。
3. 初期手札4枚・残りデッキ36枚であることを確認します。
4. ドローステップで手札が1枚増え、山札が1枚減ることを確認します。
5. 「カード一覧・詳細」で、カード名・属性・コスト・レベル表がホームのマスタに対応することを確認します。紫カードは必ず初期手札にあるわけではありません。
6. 新しいルームでは改めてシャッフルします。同じ初期手札が出る可能性もあるため、「必ず違う手札になる」は保証しません。
7. ホームを再起動しても保存デッキが残ることを確認します。
8. 両者が参加した後でホームを停止しても、進行中の試合はドロー・召喚・戦闘を継続できます。新しいルームの作成・参加は取得エラーになります。
9. 存在しないデッキIDでは開始できず、仮デッキへ置き換わらないことを確認します。

## 5. 40枚を通して確認する任意スクリプト

ホームとバトルを起動した状態で、別ターミナルから実行できます。こちらでは実行していません。

```bash
python3 battle-server/tests/home_deck.py
```

初期 `poc-001` マスタで使います。検証用デッキを1件保存し、2ルームを作成します。召喚せず全カードを引き、保存デッキの内訳と40枚の個体IDが一致すること、コスト・属性・レベル表、再送、相手の手札非公開を確認します。引いた順番も表示します。

既存の `smoke.py` / `combat.py` を使う場合も、今回からホーム起動・初期デッキ登録が必要です。デッキ切れ時は従来どおり検証停止で、敗北タイミングは変更していません。

## 公開マスタの運用

編集元は `workers/card-home-poc/data/master-poc-001.json` です。登録スクリプトが検証し、JSON本体とSHA-256をD1へ保存します。バトル側に同じカードの登録ファイルはありません。

初期化を再実行しても同一内容なら保持します。一度公開した同じバージョンの内容を変更するとDBが拒否します。変更時は以下の順序です。

1. JSONを別名で作成し、`masterVersion`も新しい値へ変更する。
2. `workers/card-home-poc` で `npm run db:seed -- data/新しいファイル.json` を実行する。
3. `wrangler.jsonc` の `MASTER_VERSION` を新しい値にしてホームを再起動する。
4. 新バージョンのデッキをホームで作成・保存する。

旧マスタ・旧保存デッキは保持します。バトルは各プレイヤーの参加時に内部APIから取得し、ルーム内でバージョンとハッシュを一致させます。取得した定義は試合中のメモリに固定します。全試合共通のマスタキャッシュはまだ設けていません。

## 今回の境界

- バトルはD1へ直接接続せず、デッキIDだけを受け付けて信頼するホームから定義を取得します。
- ホーム・バトルの両方で40枚、同名最大3枚、カード参照を検証します。
- この段階はローカル専用。ホーム画面の利用者認証・所持カードの検証・マッチメイク・署名付き参加チケットは後続です。本番では任意のデッキIDを指定できる運用にせず、ホームの認証済み対戦受付に接続します。
- 内部APIは共有キーを要求します。公開画面はlocalhost/127.0.0.1のみ受け付け、リモート公開用の設定は用意していません。
- カード効果・マジック・ネクサスは今回のランタイムでは受け付けません。Hybrid効果エンジンは次の検証です。
- イラストの参照情報はマスタへ用意しましたが、画像登録・R2配信・Unity画像表示はまだ追加していません。添付画像も変更していません。
- 既存の対戦状態はメモリ上です。バトル再起動後の試合復元は対象外です。

## 実装した主なファイル

- `workers/card-home-poc/`：ローカルWorkers、D1スキーマ、マスタ、保存デッキ編集画面
- `scripts/card-home-poc.sh`：初期化・起動
- `battle-server/HomeCatalog.cs`：認証付き取得・マスタとデッキ検証
- `battle-server/Program.cs`：保存デッキからの対戦生成、属性別軽減
- `battle-server/tests/home_deck.py`：ユーザー実行用の連携確認
- `unity/CardBattleUnity/Assets/CardBattle/Scripts/SummonPoc.cs`：デッキID指定・マスタ由来の表示

公式参考：[D1ローカル開発](https://developers.cloudflare.com/d1/best-practices/local-development/)

## 追加した仕様

- 仮カードは赤1シンボル、コスト3、赤の軽減上限2。場のシンボルが0／1／2以上なら支払いは3／2／1個。疲労していても軽減に数えます。召喚するカード自身は数えません。
- 手札にサーバーが計算した支払いコストを表示します。召喚時は別途維持コア1個が必要です。
- 自分のメインで場のカードを選ぶと「コア +1」「コア −1」を表示します。リザーブとの間で移動し、両画面へ反映します。
- カード間の移動は、移動元を選んでリザーブへ戻し、移動先を選んで載せてください。
- コア1個でLv1、2〜3個でLv2、4個以上でLv3。BPはLv1の値に対してLv2で+2000、Lv3で+4000です。戦闘も現在のBPで判定します。

- 召喚の支払い元は今回もリザーブです。場の余剰コアを使う場合、先に「コア −1」で戻してください。複数の支払い元を一括指定する召喚UIは後続実装です。

# アタック・ブロック・ライフ勝敗PoC

実装済み。今回のビルド・動作確認・テスト実行はユーザーが担当するため、こちらでは未実施。

## 追加内容

- 自分のアタックステップで、回復状態のスピリット1体を選んでアタック。召喚したターンにも攻撃可能。先攻初回は従来どおりアタックを省略。
- アタックすると疲労し、防御側の選択を待つ。選択中は次のステップや別のアタックに進めない。
- 防御側は回復状態の自分のスピリット1体を選び「ブロック」、または「ライフで受ける」を選択する。ブロッカーがいなくても「ライフで受ける」で確定する。
- ブロッカーは疲労。BPが低い側を破壊、同値なら両方を破壊。破壊したカードは持ち主の捨て札、載っていたコアは持ち主のリザーブへ移す。
- ブロックした場合は、BP差にかかわらずライフを減らさない。
- ライフで受けると攻撃側のシンボル数だけライフを減らし、そのコアを防御側のリザーブへ移す。今回の検証カードはすべて1シンボル。
- ライフ0で勝敗確定。両画面に勝利／敗北を表示し、それ以降の新しいゲーム操作を拒否する。
- 戦闘後も同じアタックステップが続き、他の回復スピリットで攻撃できる。「次のステップ」でエンドへ進む。
- 疲労したスピリットは自分の次のリフレッシュで回復する。
- 相手の攻撃カード、戦闘結果、捨て札枚数を両画面へ同期する。相手の手札内容は引き続き非公開。
- 攻撃と防御の要求にも、操作主体・盤面バージョン・バトルID・再送の検証を適用する。

5. Player 1が合計5回ライフで受けるとライフ0となり、Player 2に勝利、Player 1に敗北を表示する。以降の召喚・攻撃・防御・ステップ進行は無効。

## 確認C：操作制限

- 先攻初回の攻撃不可。
- 相手のカードを使った攻撃・ブロック不可。
- 防御選択待ちの間は次のステップへ進めない。
- ブロック可能なカードがなくてもライフで受けられる。
- 通信再試行でダメージや破壊が二重適用されない。
