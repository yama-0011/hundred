# フロントエンド ファイル命名ルール

## 1. 目的

VS Codeなどでプロダクト名・機能名をファイル検索したときに、その機能を構成するファイルを漏れなく発見しやすい状態を保つ。

本ルールでは、一般的な「名前の短さ」よりも、次の内容を優先する。

- プロダクト名・機能名で関連ファイルを検索できること
- ファイル単体を見ても所属するプロダクトや機能が分かること
- Hundred、Record Hub、Memo、Gameなどの責務を区別できること
- React / TypeScriptを学び始めた開発者が処理の流れを追いやすいこと
- ファイル数が増えても検索性を維持できること

## 2. 基本ルール

1. プロダクト専用ファイルには、配置ディレクトリにかかわらずプロダクト名を接頭辞として付ける。
2. ファイル名は原則として「プロダクト名 + サブ機能名 + 役割」の順に組み立てる。
3. プロダクト名とサブ機能名には、プロジェクト内で決めた正式表記を使用する。
4. ReactコンポーネントとクラスはPascalCase、その他のTypeScriptファイルはcamelCase、CSSはkebab-caseを使用する。
5. `utils.ts`や`types.ts`のように、所属や用途を判断できない名前を単独で使用しない。
6. 複数プロダクトから利用するファイルに、特定プロダクトの接頭辞を付けない。
7. ファイルの役割が変わった場合は、ファイル名とファイルコメントも同時に更新する。
8. `index.ts`による再エクスポートは、ファイル検索時に実体が分かりにくくなるため、必要性が明確な場合だけ使用する。

### プロダクト名の正式表記

| 表示名 | PascalCase | camelCase | kebab-case |
| --- | --- | --- | --- |
| Hundred | `Hundred` | `hundred` | `hundred` |
| Record Hub | `RecordHub` | `recordHub` | `record-hub` |
| Memo | `Memo` | `memo` | `memo` |
| Game | `Game` | `game` | `game` |
| 共通 | `Shared` | `shared` | `shared` |

`Recordhub`、`Record-Hub`、`recordhub`など、正式表記と異なる揺れを作らない。

## 3. 機能専用ファイル

Hundred、Record Hub、Memo、Gameなど、1つのプロダクトだけで使用するファイルにはプロダクト名を付ける。

基本形:

```text
プロダクト名 + サブ機能名 + 役割
```

例:

```text
HundredCursorSoundDialog.tsx
HundredWallpaperBackground.tsx
hundredCursorSoundOptions.ts
useHundredCursorSound.ts
recordHubRecordService.ts
RecordHubRecordList.tsx
```

### ディレクトリ名と重複する場合

検索性を優先し、ディレクトリ名とファイル名でプロダクト名が重複しても接頭辞を付ける。

採用する例:

```text
components/Hundred/Wallpaper/HundredWallpaperBackground.tsx
components/RecordHub/Record/RecordHubRecordList.tsx
```

避ける例:

```text
components/Hundred/Wallpaper/WallpaperBackground.tsx
components/RecordHub/Record/RecordList.tsx
```

重複を許可する理由:

- VS Codeのファイル名検索でプロダクト関連ファイルを一覧化できる
- エディターのタブだけを見ても所属が分かる
- エラーメッセージ、Git差分、レビュー画面でも所属を判断できる
- 将来ファイルを移動しても名前から責務が失われない

### サブ機能名

プロダクト内に複数の機能がある場合は、プロダクト名の後ろへサブ機能名を付ける。

```text
Hundred + CursorSound + Dialog
Hundred + Wallpaper + Background
RecordHub + Record + Service
RecordHub + Category + List
```

`HundredDialog.tsx`のようにサブ機能が分からない名前は避ける。

## 4. 共通ファイル

Hundred、Record Hub、Memo、Gameのうち、複数プロダクトから利用するファイルは`Shared`として扱う。

配置例:

```text
frontend/src/
├── components/Shared/
├── hooks/Shared/
├── services/Shared/
├── types/Shared/
└── utils/Shared/
```

命名例:

```text
SharedDialog.tsx
SharedIconButton.tsx
sharedApiClient.ts
sharedDateUtils.ts
sharedApiTypes.ts
shared-dialog.css
```

### 共通化の判断

次の条件を満たす場合だけ`Shared`へ移動する。

- 実際に2つ以上のプロダクトから利用する
- 特定プロダクトの表示、用語、業務ルールに依存しない
- propsや引数へ特定プロダクト専用の型を要求しない

「将来使うかもしれない」という理由だけで共通化しない。現在Hundredだけで使用する場合は、Hundred専用ファイルとして命名する。

### アプリケーション全体のエントリーファイル

Vite / Reactの標準的なエントリーファイルは例外として短い名前を許可する。

```text
App.tsx
main.tsx
global.css
vite.config.ts
```

これらは特定プロダクトの機能ファイルではなく、アプリケーション全体の起動や共通設定を担当する。

## 5. ファイル種別ごとの命名

### 5.1 Reactコンポーネント

PascalCaseで「プロダクト名 + サブ機能名 + UI上の役割」とする。

```text
HundredHome.tsx
HundredCursorSoundDialog.tsx
HundredWallpaperBackground.tsx
RecordHubRecordList.tsx
MemoEditorDialog.tsx
```

役割には、実際のUI構造に合う単語を使用する。

- `Page`: ルーティングされる画面
- `Layout`: 複数画面で使用する配置
- `Dialog`: モーダルダイアログ
- `Panel`: 画面内のまとまり
- `List`: 一覧
- `Item`: 一覧の1項目
- `Button`: 操作ボタン
- `Background`: 背景表示

すべてのコンポーネントへ`Component`を付ける必要はない。

### 5.2 ページ

PascalCaseで「プロダクト名 + 画面名 + Page」とする。

```text
HundredHomePage.tsx
RecordHubHomePage.tsx
RecordHubRecordDetailPage.tsx
MemoHomePage.tsx
```

`HomePage.tsx`や`DetailPage.tsx`だけでは、どのプロダクトの画面か分からないため使用しない。

### 5.3 TypeScriptの設定・定数ファイル

camelCaseで「プロダクト名 + サブ機能名 + 内容」とする。

```text
hundredCursorSoundOptions.ts
hundredWallpaperOptions.ts
hundredNavigationConstants.ts
recordHubRecordConstants.ts
memoEditorOptions.ts
```

推奨する末尾:

- `Options`: 選択肢
- `Config`: 機能設定
- `Constants`: 定数群
- `Routes`: ルート定義
- `Schema`: 入力値やデータ構造の検証定義

`config.ts`、`constants.ts`、`options.ts`だけの名前は使用しない。

### 5.4 Hook

camelCaseで`use`を先頭に置き、その直後へPascalCaseのプロダクト名と機能名を続ける。

```text
useHundredCursorSound.ts
useHundredSwipeNavigation.ts
useRecordHubRecords.ts
useMemoAutosave.ts
useSharedMediaQuery.ts
```

基本形:

```text
use + プロダクト名 + 機能名
```

`useCursorSound.ts`のように、所有するプロダクトが分からない名前は避ける。

### 5.5 型定義ファイル

camelCaseで「プロダクト名 + サブ機能名 + Types」とする。

```text
hundredWallpaperTypes.ts
hundredCursorSoundTypes.ts
recordHubRecordTypes.ts
memoEditorTypes.ts
sharedApiTypes.ts
```

1つのコンポーネント内でしか使わないprops型などは、無理に別ファイルへ分けず、そのコンポーネントファイル内へ定義する。

複数ファイルから利用する型だけを型定義ファイルへ分離する。

### 5.6 utility / helper

camelCaseで「プロダクト名 + 対象 + 処理内容」とする。

処理内容を具体的に表せる場合は、`Utils`や`Helpers`よりも具体的な名前を優先する。

```text
hundredWallpaperParser.ts
hundredNavigationCalculator.ts
recordHubDateFormatter.ts
recordHubRecordValidator.ts
sharedUrlBuilder.ts
```

複数の小さな処理をまとめる必要がある場合だけ、次を許可する。

```text
hundredWallpaperUtils.ts
recordHubRecordHelpers.ts
sharedDateUtils.ts
```

避ける例:

```text
utils.ts
helpers.ts
common.ts
```

### 5.7 service

camelCaseで「プロダクト名 + 対象 + Service」とする。

```text
hundredSettingsStorageService.ts
hundredAppLaunchService.ts
recordHubRecordService.ts
recordHubCategoryService.ts
memoStorageService.ts
sharedApiClient.ts
```

外部API専用の場合は、処理内容に応じて次の末尾を使用できる。

- `Service`: 機能単位の処理
- `Api`: API呼び出しのまとまり
- `ApiClient`: HTTP通信の共通基盤
- `StorageService`: localStorageなどの保存処理

`api.ts`、`service.ts`だけの名前は使用しない。

### 5.8 CSS

kebab-caseで「プロダクト名 + サブ機能名」とする。

```text
hundred-home.css
hundred-cursor-sound.css
hundred-wallpaper.css
record-hub-home.css
record-hub-record-detail.css
memo-editor.css
shared-dialog.css
```

特定コンポーネント専用のCSS Modulesを導入する場合は、コンポーネント名と対応させる。

```text
HundredWallpaperBackground.module.css
RecordHubRecordList.module.css
```

`styles.css`、`dialog.css`、`background.css`だけの名前は使用しない。

### 5.9 テスト

テスト対象ファイルと同じファイル名を使用し、拡張子の直前へテスト種別を付ける。

```text
HundredWallpaperBackground.test.tsx
hundredWallpaperOptions.test.ts
useHundredCursorSound.test.ts
recordHubRecordService.test.ts
HundredHome.integration.test.tsx
hundred-home.e2e.ts
```

基本形:

```text
対象ファイル名.test.ts
対象ファイル名.test.tsx
機能名.integration.test.tsx
機能名.e2e.ts
```

テストファイルだけを見ても、対象のプロダクトと機能が分かる状態にする。

### 5.10 画像・音声などのアセット

プロダクト専用アセットも、検索性が必要な場合はkebab-caseのプロダクト接頭辞を付ける。

```text
hundred-cursor-sound-block.mp3
hundred-wallpaper-aurora.webp
record-hub-empty-state.svg
memo-editor-background.webp
```

外部ライブラリの規約や自動生成ツールによって名前が決まるファイルは、その規約を優先してよい。

## 7. 避ける命名

### 所属プロダクトが分からない

```text
HomePage.tsx
WallpaperBackground.tsx
CursorSoundPicker.tsx
RecordList.tsx
```

### 役割が分からない

```text
HundredData.ts
HundredManager.ts
RecordHubCommon.ts
MemoLogic.ts
```

`Manager`、`Data`、`Logic`、`Common`などの広すぎる単語は、具体的な役割へ置き換える。

### ファイル種別しか分からない

```text
types.ts
utils.ts
helpers.ts
constants.ts
service.ts
styles.css
```

### 表記が統一されていない

```text
RecordhubHome.tsx
recordhubService.ts
record_hub_home.css
hundred_Wallpaper.ts
```

### 不要なプロダクト接頭辞

複数プロダクトで使用する共通ファイルへ、利用開始時のプロダクト名を残さない。

```text
HundredSharedDialog.tsx
hundredCommonApiClient.ts
```

共通化した場合は、次のように変更する。

```text
SharedDialog.tsx
sharedApiClient.ts
```

## 8. ファイル作成・移動時のチェック項目

ファイルを作成または移動するときに、次を確認する。

- 特定プロダクト専用か、複数プロダクトで使う共通ファイルか
- 専用ファイルに正式なプロダクト接頭辞が付いているか
- サブ機能名とファイルの役割が名前から分かるか
- ファイル種別に合った大文字・小文字形式になっているか
- 同じ意味の表記揺れが既存ファイルにないか
- `utils`、`types`、`data`など広すぎる名前だけになっていないか
- テストファイル名が対象ファイル名と対応しているか
- CSSやアセットにも必要なプロダクト接頭辞が付いているか
- ファイル移動後にimportパスを更新したか
- ファイル移動後に古いファイルや空ディレクトリが残っていないか
- ファイル先頭の「概要」「責務」が新しい名前と役割に一致しているか
- 保存済みID、URL、localStorageキーなどへファイル名変更の影響がないか
- `npm run build`と`npm run lint`を実行したか


## 読み取り専用の監査指示
以下の命名ルールを正として、Hundred関連ファイルを監査してください。
ドキュメント/コーディング規約/フロントエンド-ファイル命名ルール.md

対象:
frontend/src/components/Hundred
frontend/src/pages/Hundred
frontend/src/styles/Hundred
frontend/src/assets/Hundred

今回はファイルを変更しないでください。
以下の形式で報告してください。

- 現在のファイルパス
- ルールに適合しているか
- 推奨ファイル名
- 推奨する理由
- import修正が必要になりそうな参照元
- 判断できないもの

機械的な命名チェックと、ファイルの実際の責務に基づくチェックを分けてください。

## 確認後の修正指示
先ほどの監査結果のうち、承認したファイルだけリネームしてください。

要件:
- 処理内容は変更しない
- importパスをすべて更新する
- ファイル内の主要export名もファイル名と一致させる
- コメント内の旧名称も更新する
- localStorageキーや保存済みIDは変更しない
- 空ディレクトリを残さない
- npm run buildを実行する
- npm run lintを実行する
- Gitコミットは行わない
