# バックエンド コメント実装ルール

## 1. 目的

Spring Boot / Javaの各クラスについて、API、業務処理、データアクセスの役割をコードから追える状態を保つ。

コメントには、構文の説明ではなく、次の内容を記述する。

- 何のために存在するか
- 何を担当するか
- 業務ルールや技術上の制約

## 2. 基本ルール

1. コメントは日本語で記述する。
2. ファイル単位で「概要」と「責務」を記述する。
3. 開発者が実装したメソッド単位で「概要」と「責務」を記述する。
4. APIの入力、出力、例外などは必要に応じてJavadocタグで補足する。
5. コードを読めば明らかな処理を、行単位で説明しない。
6. 実装を変更した場合は、関連するコメントも同時に更新する。
7. 「責務外」の欄は設けない。

## 3. ファイル・クラス単位のコメント

クラス、interface、record、enumの定義直前にJavadocで記述する。

```java
/**
 * 概要:
 * PostgreSQLへの接続状態を確認するAPIを提供するController。
 *
 * 責務:
 * - DB疎通確認リクエストを受け付ける
 * - 接続中のデータベース名をレスポンスとして返す
 */
@RestController
public class DatabaseCheckController {
    // 実装
}
```

### 概要に書くこと

- クラスが何を提供するか
- Controller、Service、Repositoryなど、どの役割で使用するか

### 責務に書くこと

- クラスが担当する主要処理
- 他レイヤーとの受け渡し内容

## 4. メソッド単位のコメント

メソッド定義の直前へJavadocで記述する。

```java
/**
 * 概要: 接続中のデータベース名を取得する。
 * 責務: current_database関数を実行し、取得結果を文字列で返す。
 *
 * @return 接続中のデータベース名
 */
public String getCurrentDatabaseName() {
    // 実装
}
```

引数がある場合:

```java
/**
 * 概要: 指定されたIDの記録を取得する。
 * 責務: IDを検索条件としてRepositoryへ渡し、取得結果を返す。
 *
 * @param recordId 取得対象の記録ID
 * @return 取得した記録
 * @throws RecordNotFoundException 対象の記録が存在しない場合
 */
public Record findRecord(long recordId) {
    // 実装
}
```

## 5. 対象となる処理

次の開発者実装にはコメントを付ける。

- Controllerのエンドポイントメソッド
- Serviceの業務処理
- Repositoryのデータアクセス処理
- 設定クラスのBean生成メソッド
- データ変換、検証、計算を行うprivateメソッド
- コンストラクターに独自の初期化処理がある場合

次は原則として対象外とする。

- 自動生成されたgetter / setter
- recordが自動生成するアクセサー
- 処理を追加していない標準的なオーバーライド

ただし、業務上の意味や設計上の理由がある場合はコメントを記述する。

## 6. Controllerのコメント

HTTPメソッドやURLを読み上げるだけではなく、APIの目的を記述する。

良い例:

```java
/**
 * 概要: RDS PostgreSQLへの疎通状態を確認する。
 * 責務: 接続中のDB名を取得し、確認結果として返す。
 *
 * @return 接続中のデータベース名
 */
@GetMapping("/api/db-check")
public String checkDatabase() {
    // 実装
}
```

避ける例:

```java
/** GETリクエストを処理する。 */
```

 */

}
```

 *
 * @return 更新した行数
 */
public int updateOwnedRecord(long recordId, long userId) {
    // 実装
}
```

## 8. 処理内部のコメント

業務ルール、セキュリティ上の理由、フレームワーク固有の回避策など、コードだけでは意図が分からない場合に記述する。

良い例:

```java
// 所有者IDも条件に含め、URLのIDを書き換えた不正更新を防ぐ。
```

避ける例:

```java
// SQLを実行する。
jdbcTemplate.queryForObject(sql, String.class);
```

## 9. Javadocタグ

必要に応じて次を使用する。

- `@param`: 引数の業務上の意味、形式、単位
- `@return`: 戻り値の意味
- `@throws`: 例外が発生する条件

型名から明らかな説明だけを繰り返さない。

## 10. コメント更新チェック

実装変更時に次を確認する。

- クラスの概要と実際の役割が一致しているか
- Controller、Service、Repositoryの責務が混ざっていないか
- APIの入力、戻り値、例外条件が古くないか
- SQLや業務条件を変更した理由が必要に応じて説明されているか
- 削除した機能や旧クラス名がコメントに残っていないか
