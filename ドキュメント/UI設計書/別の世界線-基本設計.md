# 別の世界線 基本設計

## 1. 概要

### 1.1 アプリ名

**別の世界線**

### 1.2 コンセプト

> もう一人の自分の人生を観察するソーシャルシミュレーション

Hundred内のUser Appとして提供する。

ユーザーは「別の世界線」に存在するもう一人の自分を作成する。別世界の自分は、他ユーザーのキャラクターと学校で出会い、交流し、友達・親友・恋人などの人間関係を自律的に形成していく。

現実のユーザーは基本的に**観察者**であり、別世界の自分の日常的な行動や人間関係を直接操作しない。

本アプリはマッチングアプリとして設計しない。

基本体験は、

``` text
別世界で人間関係が生まれる
        ↓
「この人はどんな人なんだろう？」
        ↓
ゲーム内プロフィールを見る
        ↓
必要なら本人が登録したInstagramプロフィールを開く
```

という順序とする。

------------------------------------------------------------------------

## 2. 基本方針

### 2.1 ユーザーは観察者

ユーザーが直接決定しないものの例：

-   誰と話すか
-   誰と仲良くなるか
-   誰を好きになるか
-   誰に告白するか
-   告白を受け入れるか
-   誰と喧嘩するか
-   仲直りするか
-   別れ話をするか
-   別れるか

これらは別世界のキャラクターが自律的に判断する。

### 2.2 ユーザーが変更できるもの

ユーザーは別世界の自分の生活環境・プロフィールを設定できる。

-   名前
-   アバター
-   性別
-   趣味
-   部活
-   バイト
-   勉強の得意度
-   帰り道（地方・地域）
-   Instagramプロフィールへのリンク情報

ただし、これらの変更は人間関係に影響する可能性がある。

### 2.3 設定変更は人間関係の直接操作ではない

例えば部活を変更しても、

``` text
友情ポイント -20
```

のように直接関係値を操作しない。

``` text
部活を退部
↓
その部活の人との交流機会が減る
↓
時間経過
↓
結果として疎遠になる可能性がある
```

という形でシミュレーションへ影響させる。

## 3. 学校

### 3.1 学校数

**全ユーザーが1つの学校に所属する。**

ユーザー数に応じてクラスを増加させる。

1クラスは**約33人**を目安とする。

例：

``` text
100人
→ 約3クラス

1,000人
→ 約30クラス
```

### 3.2 学年・卒業

以下の概念は設けない。

-   学年
-   進級
-   卒業

ユーザーは入学後、継続して学校に所属する。

### 3.3 入学

「別の世界線」の利用開始を入学として扱う。

新規ユーザーは、

``` text
最後のクラスを確認
↓
空席あり
→ 最後尾の席へ着席

満席
→ 新しいクラスを作成
→ 新クラスの最初の席へ着席
```

とする。

この仕組みにより、入学時期の近いユーザーが最初のクラスメイトになりやすい。

------------------------------------------------------------------------

## 4. クラス・座席

### 4.1 クラス替え

**年1回**実施する。

既存の人間関係を考慮せず、**完全ランダム**に再編成する。

そのため、

-   親友と別クラスになる
-   恋人と別クラスになる
-   昔の友達と再び同じクラスになる
-   新しい人物と出会う

などが自然に発生する。

別クラスになっても、部活・バイト・趣味・帰り道など別の接点によって交流が続く可能性がある。

### 4.2 席替え

**月1回**実施する。

席の近さは交流機会の一つとして扱う。

ただし、

``` text
席が近い
≠
自動的に友達になる
```

とする。

------------------------------------------------------------------------

## 5. 別世界プロフィール

### 5.1 名前

別世界専用の名前をユーザーが自由に設定する。

**サービス全体でユニーク名称**とし、重複を許可しない。

本名やHundred上の名前と一致させる必要はない。

### 5.2 アバター

Tomodachi
Collectionのように、ユーザー自身が外見を作成する方式を想定する。

Unityでは共通キャラクターを使用し、顔・髪・服装等のパラメータによって外見を変更する方式を第一候補とする。

具体的なパーツ構成は詳細設計で決定する。

### 5.3 趣味

複数設定可能とする方向で設計する。

将来的には多数の趣味を扱えるよう、カテゴリ構造を検討する。

例：

``` text
ゲーム
├ RPG
├ FPS
└ カードゲーム

スポーツ
├ サッカー
├ 野球
└ バスケットボール

エンタメ
├ アニメ
├ 漫画
└ 映画
```

同じ趣味は交流のきっかけになるが、自動的な友情成立条件にはしない。

### 5.4 部活

部活はユーザー自身が設定する。

**無所属（帰宅部）も可能**とする。

所属している場合は部活仲間との交流機会が増える。

### 5.5 バイト

バイトもユーザー自身が設定する。

**バイトをしない選択も可能**とする。

バイトをしている場合はバイト仲間との交流機会が生まれる。

### 5.6 勉強

学校を舞台とするため、勉強要素を持たせる。

例：

-   とても得意
-   わりと得意
-   普通
-   少し苦手
-   苦手

勉強も交流のきっかけとして利用できる。

例：

``` text
数学が得意なA
+
数学が苦手なB
↓
教える / 教えてもらう
↓
交流機会
```

詳細な教科設定は未確定。

### 5.7 帰り道

ユーザー自身が別世界での地方・地域を設定する。

同じ方面、または帰宅ルートが重なる人物同士は交流する機会が増える。

現実の正確な住所・現在地を公開する用途には使用しない。

------------------------------------------------------------------------

## 6. プロフィール変更

プロフィール変更は単なる設定編集ではなく、別世界での生活環境の変化として扱う。

変更によって人間関係へ影響する可能性がある場合は、事前にユーザーへ説明する。

例：

``` text
現在の部活を退部すると、
部活の人たちと交流する機会が減ります。

その結果、現在の友達と疎遠になる可能性があります。

※現在の人間関係が即座に解除されるわけではありません。
```

### 6.1 部活変更

「退部」「入部」という別世界上の出来事として扱う。

履歴例：

``` text
2027/05/10 サッカー部を退部した
2027/05/18 バスケットボール部に入部した
```

### 6.2 バイト変更

退職・新しいバイト開始という生活環境の変化として扱う。

### 6.3 趣味変更

趣味の追加・削除も交流機会に影響するため、変更時に影響の可能性を表示する。

### 6.4 帰り道変更

帰り道・地域の変更は**引っ越し**として扱う。

例：

``` text
美原方面
↓
鳥取方面へ変更
↓
「鳥取方面へ引っ越した」
```

引っ越しによって、それまで一緒に帰っていた人物との交流機会が減り、新しい地域の人物との交流機会が増える可能性がある。

------------------------------------------------------------------------

## 7. 有限な交流時間

各キャラクターが他人と交流できる時間・機会は有限とする。

これにより、

> 部活・バイト・趣味などを大量に設定した人ほど有利

という状態を防ぐ。

例：

``` text
部活あり + バイトあり
→ 部活・バイト仲間との交流が増える
→ 趣味に使える時間が減る

部活なし + バイトなし
→ 部活・バイト経由の交流はない
→ 趣味の時間が増える
→ 趣味つながりの交流が増えやすい
```

部活・バイト・趣味・帰り道などは単純な加点項目ではなく、**誰と時間を過ごす可能性が高いかを変化させる要素**とする。

------------------------------------------------------------------------

## 8. 人間関係シミュレーション

### 8.1 基本モデル

``` text
接点
↓
交流機会
↓
実際の交流
↓
交流履歴
↓
人間関係の変化
```

「同じクラス +10」「同じ部活
+20」のような単純なポイント加算のみで友達を決定しない。

### 8.2 主な交流のきっかけ

-   同じクラス
-   席が近い
-   同じ部活
-   同じ趣味
-   同じバイト
-   勉強を教える / 教えてもらう
-   友達の友達
-   帰り道
-   既存の友人関係
-   偶然の交流
-   学校イベント

将来的な追加候補：

-   文化祭
-   修学旅行
-   委員会
-   体育祭
-   イベントの同一担当
-   その他期間限定イベント

### 8.3 基本的な関係

候補：

-   接点なし
-   知り合い
-   友達
-   親友
-   恋人
-   疎遠
-   過去に友達だった
-   過去に親友だった
-   元恋人

詳細な状態遷移は詳細設計で決定する。

### 8.4 友情

友達・親友などの関係そのものは**相互関係**とする。

``` text
A ── 友達 ── B
A ── 親友 ── B
```

友情について「Aは親友だと思っているがBは友達だと思っている」という非対称状態は初期設計では扱わない。

### 8.5 親友

親友はレアな関係とする。

**原則1〜3人程度に自然に収束する状態**を目指す。

単純に3人でハード制限するかどうかは未確定。

有限な交流時間などによって自然に希少性を作る。

### 8.6 疎遠・関係解除

一度友達になっても永久には維持されない。

``` text
友達
↓
クラス替え
↓
共通の接点が減る
↓
交流頻度低下
↓
疎遠
↓
友達関係解除
```

過去の関係は削除せず履歴として保持する。

そのため、

> 現在は知り合いだが、以前は親友だった

といった状態を表現できる。

再び交流が増えれば、友達・親友へ戻る可能性もある。

------------------------------------------------------------------------

## 9. 喧嘩・仲直り

友情にはマイナス方向の出来事も存在する。

``` text
友達 / 親友
↓
意見の衝突・すれ違い
↓
喧嘩
↓
交流減少
↓
├ 仲直り
│  └ 以前より仲良くなる場合もある
├ 関係は戻るが以前ほど親しくない
└ 仲直りできない
   └ 疎遠 / 関係解除
```

具体的な喧嘩理由・発生条件は詳細設計で決定する。

------------------------------------------------------------------------

## 10. 恋愛

### 10.1 基本フロー

``` text
知り合う
↓
交流
↓
気になり始める
↓
片思い
↓
恋愛感情が強くなる
↓
告白
↓
成功 / 失敗
↓
交際
```

### 10.2 恋愛感情と交際関係

**恋愛感情と交際関係を分離して管理する。**

交際関係は相互。

``` text
A ── 恋人 ── B
```

恋愛感情は非対称。

``` text
A → B：好き
B → A：好きとは限らない
```

そのため、

``` text
自分 ── 恋人 ── A

A → B：好き
```

という状態も発生可能とする。

### 10.3 片思いの公開範囲

他人が誰を好きなのかはプロフィールに公開しない。

ただし、**現実のユーザーは別世界の自分自身の恋愛感情を確認できる。**

例：

``` text
恋人：Aさん
気になる人：Bさん
```

### 10.4 交際直後

交際直後は一定期間、**ラブラブ期**のような状態を設ける。

この期間は、

-   恋人同士の交流が増えやすい
-   お互いへの恋愛感情が強い
-   他人への恋愛感情が発生しにくい

などの傾向を持たせる。

具体的な期間・数値は詳細設計で決定する。

### 10.5 交際中の別の恋愛感情

時間経過や環境変化によって、交際中でも別の人物を好きになる可能性を残す。

浮気等は頻繁に起きる仕様にはせず、**複数の状況が積み重なった結果として稀に発生する出来事**として扱う。

単純な一定確率だけでは決定しない。

考慮候補：

-   恋人との交流減少
-   クラス替え
-   別人物との継続的交流
-   恋愛感情の変化
-   現在の交際状態

### 10.6 別れ

関係値が下がった瞬間に自動破局させず、**別れ話イベント**を経由する。

``` text
交際関係悪化
↓
どちらかが別れたいと考える
↓
別れ話
↓
├ 受け入れる → 破局
├ 引き止める → 交際継続
└ 話し合う → 一旦継続
```

破局後も、

-   友達になる
-   疎遠になる
-   再び仲良くなる
-   復縁する

などの可能性を持たせる。

### 10.7 恋愛も完全自律

告白・返事・別れ話等について、現実のユーザーには選択させない。

別世界の自分自身が自律的に判断する。

------------------------------------------------------------------------

## 11. 「2人の記録」

人間関係では結果だけでなく、**その関係になった過程**を重要なコンテンツとして扱う。

例：

``` text
4月8日   同じクラスになった
5月12日  共通の友達を通じて初めて話した
6月3日   席替えで隣になった
6月18日  よく話すようになった
7月2日   一緒に帰った
7月21日  友達になった
9月14日  同じバイト先になった
12月7日  親友になった
```

関係悪化も記録する。

``` text
2月3日   喧嘩した
2月18日  仲直りした
```

過去の関係も残す。

``` text
2027/04/01 クラスが別々になった
2027/08/03 友達関係ではなくなった
2028/04/01 再び同じクラスになった
2028/05/07 再び友達になった
```

### 11.1 閲覧範囲

閲覧できる詳細履歴は、

**自分 ↔ その人物**

のみとする。

他人同士の詳細な「2人の記録」は閲覧できない。

教室内のキャラクターをタップするとゲーム内プロフィールを表示する。

例：

``` text

趣味
ゲーム / アニメ / 映画

バイト
カフェ

勉強
わりと得意

帰り道

恋人：Aさん

```

### 12.1 特別な関係

他人の友達一覧をすべて公開する必要はない。

プロフィールでは主に、

-   恋人
-   親友

を表示する。

片思い相手は表示しない。

### 12.2 接点のない人物

自分と一度も交流したことがない人物でもプロフィールを閲覧できる。

``` text
あなたとの関係
まだ接点がありません
```

プロフィール閲覧自体は別世界の人間関係に影響しない。

## 13. Instagramへの導線

### 13.1 API連携を前提にしない

「別の世界線」では、Instagram Graph
API等を利用してInstagram内部データを取得することを基本要件としない。

Instagram Business /
Creator等のプロフェッショナルアカウント化を一般ユーザーへ要求しない。

### 13.2 登録方式

ユーザー自身が、公開したいInstagramプロフィールのユーザー名またはプロフィールリンクを登録する方式とする。

概念例：

``` text
Instagramユーザー名
@yama_xxxx
        ↓
Hundred側に登録
        ↓
他ユーザーが
「Instagramを見る」
        ↓
Instagramプロフィールを外部で開く
```

Hundred側で必要なのは、Instagramプロフィールへ遷移するための情報のみとする。

### 13.3 APIを使用しないもの

初期設計では以下を不要とする。

-   Instagram OAuthによるアカウント連携
-   Instagram Graph APIによるプロフィール取得
-   Instagramアクセストークン
-   Business / Creatorアカウント必須化
-   投稿データ取得
-   フォロー関係取得

### 13.4 公開

自分と別世界上で接点のない人物であっても、そのユーザーがInstagramプロフィールを公開していれば「Instagramを見る」からアクセスできる。

Instagramリンクの登録・公開は本人の意思を前提とする。

## 14. 3D教室

### 14.1 表現

Tomodachi
Collectionのように、約33人のキャラクターがそれぞれ独立して生活しているように見える3D教室を目標とする。

想定行動：

-   歩く
-   座る
-   誰かと話す
-   2〜5人程度で集まる
-   グループへ参加する
-   グループから離れる
-   一人で過ごす
-   表情を変える

### 14.2 現在の世界を観察

教室は過去イベントの再生画面ではなく、**現在の別世界を覗く画面**とする。

``` text
自分 → Aと会話
B → 着席
C・D・E → グループで会話
F → 一人で移動

しばらくすると

自分 → 着席
D → グループを離れる
G → C・Eの会話へ参加
```

過去の出来事は履歴から確認する。

### 14.3 毎日教室にいる

現実の曜日・休日にかかわらず、教室を開けばキャラクターを観察できる。

学校生活を厳密に再現することより、いつでも人間関係を観察できるゲーム体験を優先する。

## 15. 教室移動UI

### 15.1 廊下

クラス選択画面として廊下を用意する。

``` text
┌─────────────────────┐
│        廊下          │
│                     │
│      ┌────────┐     │
│      │ Aクラス │     │
│      │   扉    │     │
│      └────────┘     │
│                     │
│    ← スライド →      │
└─────────────────────┘
```

左右へスライドすると、

``` text
Aクラス
↓
Bクラス
↓
Cクラス
```

のように扉が切り替わる。

扉をタップすると対象クラスの3D教室を表示する。

### 15.2 「移動」の意味

これは別世界のキャラクターを歩かせて別クラスへ移動する操作ではない。

**現実側の観察者が表示対象の教室を切り替える画面遷移**である。

### 15.3 他クラス

自分の所属クラス以外も自由に閲覧できる。

別クラスのキャラクターをタップしてプロフィールを見ることもできる。

### 15.4 自分のクラスへ戻る

どのクラスを閲覧していても、**自分のクラスへ即座に戻れる操作**を用意する。

ユーザー数が非常に増えた場合の検索・高速ジャンプ等は将来検討とする。

## 17. 学校イベント

将来的なアップデートでは、ミニゲームを増やすことよりも、**新しい交流のきっかけを追加すること**を重視する。

例：

### 文化祭

``` text
文化祭
```

## 19. Unity基本方針

3D教室には**Unity WebGL**を第一候補とする。

HundredのReact画面からUnity WebGLを表示するハイブリッド構成とする。

キャラクターは共通Prefabを使用する方向とする。

``` text
Character.prefab
├ Avatar
├ Animator
├ Movement
├ LookAt
└ CharacterView
```

モーション候補：

-   Idle
-   Walk
-   Sit
-   Talk
-   JoinGroup
-   LeaveGroup
-   表情変化

全員が同時に同じ行動をして機械的に見えないよう、Idle時間・移動開始・会話タイミング等に自然な揺らぎを持たせる。

NavMesh等の具体的な方式はPoCで決定する。

## 24. プライバシー・安全性

本アプリでは現実のユーザー同士を扱うため、**別世界の関係と現実の関係を明確に区別する。**

特に、

-   恋人
-   片思い
-   浮気
-   喧嘩
-   破局

などは、別世界のシミュレーションによって生成されたフィクション上の出来事であり、現実のユーザー本人の感情・関係を表すものではないことを明示する。

Instagramプロフィールへのリンクは本人が登録・公開したもののみ使用する。

帰り道についても、現実の正確な住所・位置情報を公開する設計にはしない。

恋愛関連の参加・公開範囲などは、実装前に詳細な安全・プライバシー設計を行う。

## 27. 設計上の重要原則

1.  **ユーザーは観察者である。**
2.  **人間関係は結果だけでなく過程を楽しむ。**
3.  **接点と友情成立を分離する。**
4.  **人間関係は永久ではない。**
5.  **全員と友達になる設計にしない。**
6.  **親友には希少性を持たせる。**
7.  **恋愛感情と交際関係を分離する。**
8.  **別世界の自分は恋愛を含めて自律的に判断する。**
9.  **プロフィール変更は交流環境を変えるが、人間関係を直接操作しない。**
10. **サーバーが世界の正しい状態を持ち、Unityは表現を担当する。**
11. **別世界の関係と現実の人間関係を明確に区別する。**
12. **InstagramはAPI連携ではなく、本人が登録したプロフィールへの外部リンクを基本とする。**

## 28. PoC・今後の進め方

いきなり全機能を実装せず、小さく検証する。

``` text
Step 1
クラス・ユーザー・座席の最小データモデル

Step 2
約33人の簡易シミュレーション

Step 3
接点 → 交流 → 友達化の最小ロジック

Step 4
大量シミュレーションで人間関係分布を確認

Step 5
Unityで約33人の3D教室PoC

Step 6
Workers / D1 ↔ Unity WebGL連携

Step 7
プロフィール / 「2人の記録」

Step 8
喧嘩・恋愛等を段階的に追加
```

シミュレーションについては本番投入前に大量試行し、

-   全員が友達になっていないか
-   親友が増えすぎないか
-   孤立する人物が極端に多くないか
-   人間関係が固定化しすぎないか
-   クラス替えで適度に関係が変化するか
-   恋愛・喧嘩等が頻発しすぎないか
-   長期間プレイしたときに関係履歴が面白くなるか

を検証しながら調整する。
