# オンラインカードゲーム 最小対戦仕様書

状態：ドラフト（会話での合意・採用案・未確定事項を整理）

## 1. 目的と方針

初期のバトルスピリッツをイメージした、2人で一戦を終えられるオンラインカードゲームを作る。特定年代の公式ルールを完全再現したと断定せず、本書に採用したルールを実装の基準とする。

Unity / C#（WebGL）を表示・入力、ASP.NET Core / C#を状態管理・ルール判定に使用する。まずローカル環境で検証する。AWS、DB、認証、マッチング、演出強化は初回の通信PoCには含めない。

## 2. 最小対戦の範囲

初期実装案は効果のないスピリットによる対戦とする。召喚、軽減、コア移動、レベル・BP、ターン進行、アタック、ブロック、退場、勝敗判定を実装する。

カード種別としてスピリット・マジック・ネクサスを定義する。マジック・ネクサスの使用処理とカード効果は後続実装とし、最小対戦のデッキには含めない。

ソウルコア、ブレイヴ、アルティメットなどの追加要素は初期実装に含めない。バーストとカウントはユーザー指定により保留し、初期UIでも非表示とする。第2メインステップは設けない。

## 3. カード情報

| 項目 | 内容 |
|---|---|
| カードID・名前 | 定義を識別するIDと表示名 |
| イラスト | 画像参照。PoCでは仮画像でよい |
| タイプ | スピリット・マジック・ネクサス |
| 属性 | 赤・紫・緑・白・黄・青 |
| 系統 | 竜・魚など。名称一覧は別途決定 |
| コスト | 軽減前の支払い数 |
| 軽減シンボル | 色ごとの軽減上限 |
| レベル定義 | レベルごとの必要コア数とBP。BPはスピリットに使用 |
| シンボル | 色と数。軽減およびライフ減少に参照 |
| 効果 | 表示テキストと処理定義。実装は後回し |

カード定義とは別に、各カード個体のID、所有者、所在、載っているコア数、回復／疲労状態を保持する。現在のレベルとBPは定義とコア数から求める。

| 項目 | 仕様・状態 |
|---|---|

| 初期手札 | 4枚 |
| 初期ライフ | 通常コア5個 |
| 初期リザーブ | 通常コア4個を採用案とする |
| フィールド・トラッシュ | 空 |
| デッキ順 | サーバー側でシャッフル |
| 先攻・後攻の決め方 | 未確定。通信PoCでは固定して検証可能 |
| 初期手札の引き直し | 未確定 |

## 5. ターン進行

| 順番 | ステップ | 基本処理 |
|---|---|---|
| 1 | スタート | ターン開始 |
| 2 | コア | ボイドから自分のリザーブへ通常コア1個 |
| 3 | ドロー | 自分のデッキから1枚引く |
| 4 | リフレッシュ | 自分の疲労カードを回復し、自分のトラッシュのコアをリザーブへ戻す |
| 5 | メイン | 召喚とコア移動。後続実装で配置・マジック使用を追加 |
| 6 | アタック | 任意の回数、回復状態のスピリット1体ずつで攻撃 |
| 7 | エンド | ターン終了後、相手へ交代 |

先攻の最初のターンだけコア・アタックステップを飛ばす。ドローは行う。後攻は最初のターンから攻撃できる。

効果のない最小対戦では、選択不要のステップは自動進行するUI案とする。内部では各ステップを区別する。

## 6. コアと召喚

- ボイドは盤面外のコア供給元として扱う。
- 使用カードの軽減シンボルに対応する、自分の場のシンボルを数える。各色の軽減上限まで軽減し、支払いは0未満にならない。
- 支払いに使えるのはリザーブと自分のフィールドのカード上のコア。支払ったコアは自分のトラッシュへ移す。
- 召喚コストとは別に、召喚するスピリットへLv1以上の維持に必要なコアを載せる。
- メインステップ中は、リザーブと自分のフィールドのカード間でコアを移動できる。
- コア数に応じてレベルとBPを更新する。
- コア不足による退場の詳細、特に「破壊」との区別は初期ルールの確認後に確定する。現行の「消滅」処理を無条件には採用しない。

召喚は、支払い元と召喚後に載せるコアを選び、確定する操作案とする。サーバーは操作全体を検証し、不成立なら途中の変更を残さず拒否する。

## 7. 戦闘

1. 攻撃側が回復状態のスピリットを1体選び、疲労させる。そのターンに召喚したスピリットも攻撃可能。
2. 防御側が回復状態のスピリット1体でブロックするか、ライフで受けるかを選ぶ。ブロックするスピリットは疲労する。
3. ブロックした場合、BPが低い側を破壊する。同値なら両方を破壊する。破壊カードはトラッシュ、載っていたコアは持ち主のリザーブへ移す。
4. ブロックしなかった場合、攻撃側のシンボル数だけ防御側のライフを減らし、そのコアを防御側のリザーブへ移す。
5. 勝敗を確認し、対戦継続なら次のアタックまたはアタックステップ終了を選ぶ。

最小対戦では効果を扱わないため、フラッシュの操作待ちは設けない。効果実装時には発動タイミングと解決順序を別途設計する。

## 8. 勝敗

- ライフ0で敗北。
- デッキ切れで敗北。ただし、0枚になった瞬間か、特定ステップの判定かなど、正確な判定タイミングは未確定。
- 降参、切断時の敗北、操作タイムアウトは後続仕様とする。

## 9. 盤面UI

ユーザー提供の `playsheet_w_countarea.pdf` を配置基準とする。

| 位置 | 表示 |
|---|---|
| 中央 | フィールド |
| 左下 | ライフ、その下にリザーブ |
| 右上 | デッキと残り枚数 |
| 右下 | トラッシュ。捨て札と使用済みコアを分ける |
| フィールド右側 | 7ステップと現在位置 |

バースト・カウントの枠は初期UIでは非表示。

オンライン向け追加UI案：画面下部に自分の手札、上部に相手盤面と裏向きの手札を表示する。カード選択時の詳細表示、ステップ終了、攻撃、ブロック、ライフで受ける、操作確定・取消を用意する。ボイドからのコア追加は自動処理とし、専用の操作領域は不要とする。

## 10. サーバーの責務

- 対戦ごとのカード、コア、ターン、ステップ、戦闘中の選択待ち、勝敗を管理する。
- クライアントは操作要求を送り、サーバーが手番、所有権、コスト、選択対象などを検証する。
- 同じ要求の二重適用や、古い盤面に基づく操作を防ぐ。
- 全体状態とプレイヤー別の表示情報を分ける。相手の手札内容やデッキ順は送信しない。
- コア移動で意図しない増減がないことを確認する。ボイドからの追加以外は領域間の移動として処理する。

## 11. 実装順序と完了条件

### 通信PoC

1. ローカルASP.NET Coreに、召喚可能な手札とリザーブを用意する。
2. Unityから召喚要求を送る。
3. サーバーが支払いと維持コアを検証し、状態を更新する。
4. Unityに手札・フィールド・リザーブ・トラッシュを反映する。
5. 不正な要求を拒否し、状態が変わらないことを確認する。
6. Unity WebGLでも同じ処理を確認する。

最初の完了条件は「カード1枚の召喚とコア移動が、サーバー判定に基づいてブラウザ上に正しく反映されること」。仮のカードと簡素な画面で検証する。

### 最小対戦

未確定ルールを確定後、2クライアントへ拡張し、ターン・戦闘・勝敗を実装する。両画面で公開情報が一致し、非公開情報が漏れず、一戦が終了することを完了条件とする。

## 12. 未確定事項

- 初期リザーブ4個の正式採用。
- 同名最大3枚という解釈の確認。
- 先攻・後攻の決定方法と手札の引き直し有無。
- デッキ切れの正確な敗北判定タイミング。
- コア不足による退場と、破壊の扱い。
- 最小対戦に使うカード定義とデッキ内容。
- Unity・.NETのバージョン、通信方式、既存リポジトリへの配置。

これらは通信PoCで必要な条件を固定して検証できるが、最小対戦の完成前に確定する。
