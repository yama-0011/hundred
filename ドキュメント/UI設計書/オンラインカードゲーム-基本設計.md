# オンラインカードゲーム 基本設計書

## 1. 文書概要

### 1.1 目的

本書は、Hundred上で提供するオンラインカードゲームの技術検証および今後の実装に向けて、現時点で合意した基本方針を整理するものである。

本ゲームはカードゲームのルール・ゲームシステムを題材とした学習用／個人開発プロジェクトとして構築し、将来的なオンライン対戦、演出強化、マルチプラットフォーム展開を考慮する。

### 1.2 現在のフェーズ

現在は基本方針の検討を完了し、技術検証（PoC）へ移行する段階とする。

詳細なカードルール、カード効果エンジン、DB構成、AWSサービス構成等は、技術検証の結果を踏まえて決定する。

------------------------------------------------------------------------

## 2. システム概要

### 2.1 基本コンセプト

-   オンライン対戦型カードゲームとする。
-   ゲームクライアントには Unity を採用する。
-   バトルサーバーには ASP.NET Core を採用する。
-   クライアントとサーバーはいずれも C# を中心に構成する。
-   ゲームの正しい状態はサーバー側で管理する「サーバー権威型」を基本方針とする。
-   Hundredのホーム・ゲーム起動等のWeb機能は既存のCloudflare基盤を利用する。
-   バトルサーバーはAWS上で常時稼働させる構成を第一案とする。

### 2.2 想定構成

``` text
[Hundred / Home]
React + TypeScript
Cloudflare Pages / Workers
        |
        | ゲーム起動・ホーム機能
        v
[Game Client]
Unity / C#
WebGL
        |
        | オンライン通信
        v
[Battle Server]
ASP.NET Core / C#
AWS
        |
        v
[Database]
詳細は技術検証後に決定
```

## 4. クライアント・サーバー責務

### 4.1 Unityクライアント

Unityは主に表示・入力・演出を担当する。

想定責務： - カード表示 - 手札・フィールド等の盤面表示 -
プレイヤー操作受付 - アニメーション - エフェクト - SE / BGM -
サーバーへのGameAction送信 - サーバーから受信したGameStateの表示

### 4.2 ASP.NET Coreバトルサーバー

バトルサーバーをゲームルール上の正とする。

想定責務： - 対戦状態管理 - ターン管理 - フェーズ管理 - 行動可能判定 -
コスト判定 - カード効果処理 - 勝敗判定 - GameState更新 -
不正な操作要求の拒否 - 対戦相手への状態／イベント通知

### 4.3 基本通信イメージ

``` text
Unity
「CARD-001を使用したい」
        |
        v
ASP.NET Core
- 手札に存在するか
- 現在使用可能なフェーズか
- コストを支払えるか
- その他のルールに違反しないか
        |
        v
GameState更新
        |
        v
各Unityクライアントへ結果通知
        |
        v
Unityで盤面更新・演出
```

クライアントから送信されたコスト、能力値、ダメージ値等をそのまま信用せず、サーバー側のカード定義およびGameStateを基準に判定する。

## 6. カード設計

### 6.1 カードマスター

カードには少なくとも以下のような情報を持たせることを想定する。

``` text
cardId
name
cost
attribute
type
status / BP等
effect
illustration
```

正式な項目はカードルール確定後に決定する。

### 6.2 カードマスターの正本

Cloudflare、Unity、AWSでカード情報が必要になる可能性があるため、カードマスターを複数箇所で手作業管理することは避ける。

「Single Source of
Truth（正本を1つにする）」ことを基本方針とし、具体的な保存・配布方式は技術検証フェーズで決定する。

カードマスターのバージョン管理も検討する。

例：

``` text
cardMasterVersion = 1
```

### 6.3 カード効果

第一案として「データ駆動 +
特殊効果コード」のハイブリッド方式を採用する。

汎用的な効果はデータとして定義する。

例：

``` json
{
  "trigger": "ON_SUMMON",
  "target": "OPPONENT_UNIT",
  "action": "DAMAGE",
  "value": 3000
}
```

データ定義だけでは表現が困難な特殊カードについては、C#による専用ロジックを実装できる構成を検討する。

``` text
CardDefinition
      |
      +-- Trigger
      +-- Condition
      +-- Target
      +-- Action
      |
      +-- 汎用Effect
      |
      +-- Custom Effect (C#)
```

詳細なEffect Engineの設計は実装時に検討する。

## 7. カードイラスト

### 7.1 初期方針

カードイラストは生成AIを利用して作成する。

### 7.2 画像とカードUIの分離

生成AIには原則としてイラスト部分のみを生成させる。

カード名、コスト、能力値、効果テキスト、カード枠等はUnity側で構成する。

``` text
[AI生成]
カードイラスト
      +
[Unity]
カード枠
カード名
コスト
能力値
効果テキスト
      =
ゲーム内カード表示
```

これにより、ゲームバランス調整やテキスト変更時にイラストを再生成する必要をなくす。

HundredのホームおよびWeb系機能には既存のCloudflare基盤を利用する。

想定： - Cloudflare Pages - Cloudflare Workers - その他既存Hundred基盤

### 8.2 AWS

オンライン対戦用ASP.NET
CoreサーバーはAWS上で常時稼働させる構成を第一案とする。

具体的なAWSサービスは未決定。

候補例： - EC2 - ECS / Fargate - その他ASP.NET

### 8.3 サーバーレスとの役割分担

ゲーム全体を常時稼働サーバーだけで構成する必要はない。

``` text

- オンライン対戦
- GameState
- リアルタイム通信

```

## 9. 技術検証計画

### 9.1 PoCの目的

最初の技術検証では、本格的なカードゲームを実装することを目的としない。

以下の技術構成が成立することを確認する。

``` text
Unity / C#
    |
    v
ASP.NET Core / C#
    |
    v
サーバー側GameState更新
    |
    v
Unityへ反映
```

### 9.2 最初の検証シナリオ

初期状態：

``` text
Player
Life = 5
Cost = 5
Hand = [CARD-001]

CARD-001
Cost = 3
```

操作：

``` text
Unity
CARD-001使用要求
        |
        v
ASP.NET Core
- 手札存在確認
- コスト確認
- 使用可能判定
        |
        v
GameState更新
Cost: 5 -> 2
HandからCARD-001を削除
FieldへCARD-001を追加
        |
        v
Unityへ結果返却
        |
        v
Unityの盤面更新
```

### 9.3 検証ステップ

1.  UnityからローカルASP.NET Coreへ接続する。
2.  1クライアントからGameActionを送信する。
3.  ASP.NET CoreでGameStateを更新する。
4.  更新結果をUnityへ反映する。
5.  2クライアントを接続する。
6.  リアルタイムでGameStateを共有する。
7.  切断・再接続の基本動作を確認する。
8.  Unity WebGLからASP.NET Coreへの通信を確認する。
9.  ASP.NET CoreをAWSへ配置する。
10. Unity WebGLからAWS上のバトルサーバーへ接続する。

次工程は技術検証（PoC）とする。

最初の完了条件は、

**「UnityからASP.NET
Coreへカード使用要求を送り、サーバー側でGameStateを更新し、その結果をUnityへ反映できること」**

とする。

この段階ではAWS、DB、本格的なカード効果、生成AIイラスト等を必須とせず、Unity +
ASP.NET Coreという中核構成の成立確認を優先する。
